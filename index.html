Apache Spark — Complete Summary

The big picture: Apache Spark is a distributed processing engine. It reads data, divides it into partitions, processes those partitions in parallel across executors, and writes or returns the result.

Spark execution in one view

PySpark Code
    ↓
SparkSession
    ↓
DataFrame / RDD Operations
    ↓
Transformations build a logical plan
    ↓
Lazy Evaluation
    ↓
DAG / Execution Plan
    ↓
Action triggers execution
    ↓
Job → Stages → Tasks → Executors
    ↓
Shuffle when required
    ↓
Final Result

Interview-ready summary

When a Spark DataFrame transformation is defined, Spark builds a logical execution plan because of lazy evaluation. When an action is called, the driver creates a job from the DAG. The job is divided into stages based on shuffle boundaries, and each stage is divided into tasks that process partitions in parallel on executors. Wide transformations such as groupBy and joins may trigger shuffles, while narrow transformations such as filter and select generally do not.

Final mental model: Spark builds an optimized plan first, divides work into stages and tasks, processes partitions in parallel, shuffles only when required, and returns the result.

Perfect. This is the core foundation of Spark. If you understand these concepts properly, the rest of Azure Databricks—DataFrames, Delta Lake, optimization, joins, performance tuning—will become much easier.

I'll explain them in the order that makes the most sense, not just the order listed.

First, build the complete mental picture

Imagine you have a huge dataset:

sales.csv = 1 TB

You want to:

Read → Filter → Join → Group By → Save

Spark needs to answer:

  1. Which machines will process the data?
  2. How will the data be divided?
  3. What operations should happen first?
  4. When should actual computation begin?
  5. How can the work be parallelized?
  6. Which operations require data movement between machines?
  7. How can repeated calculations be avoided?

Every concept in your list answers one of those questions.

1. What is Apache Spark?

Apache Spark is an open-source distributed computing engine used for processing large datasets across multiple machines.

Simple example

Without Spark:

100 GB data
    ↓
One machine processes everything

With Spark:

100 GB data
    ↓
Partition into chunks
    ↓
Machine 1 → 25 GB
Machine 2 → 25 GB
Machine 3 → 25 GB
Machine 4 → 25 GB
    ↓
Parallel processing

Important:

Spark is not a database.

Spark is not primarily a storage system.

Spark is a processing engine.

It reads data from systems such as:

  • ADLS Gen2
  • S3
  • HDFS
  • Azure SQL
  • Kafka
  • Delta tables
  • Parquet files

Then processes it.

2. Spark Architecture

This is one of the most important topics in the entire course.

Understand this diagram:

                    SPARK APPLICATION
                           |
                           v
                       DRIVER
                           |
                    SparkSession
                           |
                    SparkContext
                           |
                    Cluster Manager
                           |
          +----------------+----------------+
          |                |                |
          v                v                v
      Executor 1       Executor 2       Executor 3
          |                |                |
       Tasks            Tasks            Tasks
          |                |                |
       Data             Data             Data

Let's understand each component.

Driver

The Driver is the brain of the Spark application.

It:

  • Runs your main application code
  • Creates the SparkSession
  • Builds execution plans
  • Converts operations into jobs
  • Coordinates executors
  • Tracks task execution

Example:

df = spark.read.parquet("/data/sales")
df.filter("amount > 1000").show()

The driver is responsible for coordinating this application.

Analogy

Driver = Manager
Executors = Workers

The manager decides what work needs to happen.

Workers perform the actual data processing.

Executors

Executors are processes running on worker machines.

They:

  • Execute tasks
  • Process partitions
  • Store cached data
  • Return results to the driver

Example:

Executor 1 → Processes partition 1, 2
Executor 2 → Processes partition 3, 4
Executor 3 → Processes partition 5, 6

Important interview point

The driver coordinates the work, while executors perform the actual distributed data processing.

Cluster Manager

The cluster manager allocates resources.

Examples:

  • Standalone
  • YARN
  • Kubernetes
  • Databricks-managed cluster infrastructure

In Azure Databricks, Databricks manages much of this infrastructure for you.

3. SparkSession

This is the first Spark object you will frequently use in PySpark.

from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("MyApplication") \
    .getOrCreate()

What is SparkSession?

SparkSession is the main entry point for working with Spark SQL, DataFrames, and modern Spark applications.

Think of it as:

SparkSession = Your gateway into Spark

Through it, you can:

df = spark.read.csv(...)
spark.sql("SELECT * FROM sales")
spark.createDataFrame(...)

Why was SparkSession introduced?

Older Spark versions commonly used separate entry points:

  • SQLContext
  • HiveContext
  • SparkContext

SparkSession unified many of these capabilities.

Simple mental model

SparkSession
    |
    +-- Read data
    +-- Execute SQL
    +-- Create DataFrames
    +-- Access Spark configuration
    +-- Manage Spark application interaction

Important distinction

SparkSession is not the executor.

SparkSession is not the cluster.

SparkSession is the entry point/API object used by your application.

4. RDD vs DataFrame vs Dataset

This is a very common interview question.

Let's start with the evolution.

RDD
 ↓
DataFrame
 ↓
Dataset

But this does not mean RDD became obsolete.

RDD — Resilient Distributed Dataset

Resilient Distributed Dataset

RDD is Spark's original distributed data abstraction.

It is:

  • Distributed
  • Immutable
  • Fault-tolerant
  • Partitioned
  • Processed in parallel

Example:

rdd = spark.sparkContext.parallelize([1, 2, 3, 4, 5])
rdd.map(lambda x: x * 2).collect()

Result

[2, 4, 6, 8, 10]

RDD mental model

RDD = Distributed collection of objects

It does not inherently understand structured columns like:

customer_id | name | salary

DataFrame

A DataFrame is a distributed collection of data organized into named columns.

Example:

df = spark.read.parquet("/data/employees")

DataFrame:

+----+-------+------+
| id | name  |salary|
+----+-------+------+
| 1  | John  |50000 |
| 2  | Alice |70000 |
+----+-------+------+

DataFrame mental model

DataFrame = Distributed table with columns

DataFrames allow Spark to understand:

  • Schema
  • Column types
  • Expressions
  • Query plans
  • Optimization opportunities

This is why DataFrames are generally preferred for modern Spark data engineering.

Dataset

Dataset combines aspects of:

  • DataFrame
  • Strong typing

It is mainly relevant to Scala and Java.

PySpark does not provide the same strongly typed Dataset API as Scala/Java.

Practical advice

For your Azure Data Engineer course:

Focus heavily on DataFrames. Understand RDDs conceptually. Dataset is mainly important for Scala/Java interviews.

Comparison

FeatureRDDDataFrameDataset
AbstractionDistributed objectsDistributed tableTyped distributed objects
SchemaNo enforced schemaYesYes
OptimizationLimited compared to DataFrameCatalyst optimizerCatalyst optimizer
Ease of useLowerHighHigh
PySpark usageAvailableMost commonNot equivalent to Scala Dataset
Typical modern usageSpecialized casesStandard data engineeringMostly Scala/Java

Best practical rule

Use DataFrames by default. Use RDDs when you have a specific low-level requirement.

5. Transformations vs Actions

This is fundamental.

Suppose:

df = spark.read.parquet("/data/sales")

Then:

filtered_df = df.filter("amount > 1000")

Has Spark actually processed all the data?

Not necessarily.

These are transformations.

Transformations

Transformations define how data should be changed.

Examples:

df.select("name")
df.filter("salary > 50000")
df.withColumn("bonus", df.salary * 0.1)
df.groupBy("department").count()

Transformations produce a new DataFrame/RDD.

They do not immediately execute the complete computation.

Examples

  • select
  • filter
  • where
  • withColumn
  • drop
  • join
  • groupBy
  • orderBy
  • distinct
  • union

Actions

Actions trigger actual execution.

Examples:

df.show()
df.count()
df.collect()
df.write.parquet(...)
df.first()

Important

Transformations build the plan. Actions trigger execution.

6. Lazy Evaluation

This is directly connected to transformations and actions.

Example

df = spark.read.parquet("/data/sales")

filtered = df.filter("amount > 1000")

selected = filtered.select("customer_id", "amount")

At this point, Spark generally has not processed every row.

It has built a logical plan.

Read sales
   ↓
Filter amount > 1000
   ↓
Select customer_id, amount

Then:

selected.show()

Now Spark executes the required computation.

Why is this useful?

Because Spark can optimize the entire plan before execution.

For example:

df.filter("amount > 1000").select("customer_id")

Spark can potentially:

  • Read only required columns
  • Push filters closer to the data source
  • Eliminate unnecessary operations
  • Optimize execution order
  • Reduce data movement

This is one reason DataFrames are powerful.

Simple analogy

Instead of immediately doing every instruction:

"First understand the complete task, optimize it, then execute."

7. DAG — Directed Acyclic Graph

This sounds complicated but is actually simple.

A DAG is a graph representing the sequence of operations Spark needs to perform.

Example

df = spark.read.parquet("sales")

result = (
    df.filter("amount > 1000")
      .select("customer_id", "amount")
      .groupBy("customer_id")
      .sum("amount")
)

result.show()

Conceptually Spark builds:

Read Data
    ↓
Filter
    ↓
Select
    ↓
GroupBy
    ↓
Aggregate
    ↓
Show Result

This is a DAG.

Directed

Operations have a direction.

Acyclic

There are no loops/cycles in the execution graph.

Graph

Nodes and edges represent operations and dependencies.

Why DAG matters

Spark does not blindly execute your code line by line.

It creates an execution plan.

Then it optimizes that plan.

Then it divides it into stages.

This leads to the next concept.

8. Jobs, Stages, Tasks

This is one of the most important Spark architecture topics.

The hierarchy is:

Application
   ↓
Job
   ↓
Stage
   ↓
Task

Remember this exactly.

Application

Your complete Spark program.

Example:

df = spark.read.parquet(...)
df.filter(...)
df.groupBy(...)
df.write.parquet(...)

That entire program is an application.

Job

A job is triggered by an action.

Example:

df.count()

This may trigger one Spark job.

df.write.parquet(...)

This may trigger another job.

Important

One action generally triggers a Spark job.

Stage

A job is divided into stages.

Stages are created based largely on shuffle boundaries.

Example:

Read
 ↓
Filter
 ↓
GroupBy
 ↓
Write

The groupBy may require a shuffle.

So Spark may divide the work:

Stage 1:
Read → Filter

Shuffle

Stage 2:
GroupBy → Write

Task

A task is the smallest unit of work sent to an executor.

Usually:

One task processes one partition for a stage.

Example:

Stage 1 has 4 partitions

Partition 1 → Task 1
Partition 2 → Task 2
Partition 3 → Task 3
Partition 4 → Task 4

These tasks run in parallel.

Complete hierarchy

Spark Application
      |
      +-- Job 1
      |     |
      |     +-- Stage 1
      |     |     +-- Task 1
      |     |     +-- Task 2
      |     |     +-- Task 3
      |     |
      |     +-- Stage 2
      |           +-- Task 1
      |           +-- Task 2
      |
      +-- Job 2

Interview answer

A Spark application can contain multiple jobs. Jobs are divided into stages based on shuffle boundaries, and each stage contains tasks that process individual partitions in parallel.

9. Narrow vs Wide Transformations

This is critical for performance.

The question is:

Does this operation require data to move between partitions/machines?

Narrow Transformation

A narrow transformation is one where each output partition depends on a small number of input partitions, typically one.

No major data redistribution is required.

Examples:

filter()
select()
map()
withColumn()

Example

Partition 1 → Filter → Partition 1
Partition 2 → Filter → Partition 2
Partition 3 → Filter → Partition 3

No need to move data across the cluster.

Why fast?

Because it can be processed independently.

Wide Transformation

A wide transformation requires data to be redistributed across partitions.

This is called a shuffle.

Examples:

groupBy()
join()
distinct()
orderBy()
repartition()

Example: groupBy

Suppose data is distributed like this:

Partition 1:
customer A
customer B

Partition 2:
customer A
customer C

Partition 3:
customer B
customer C

To calculate total per customer, all records for the same customer need to come together.

Customer A → Same partition
Customer B → Same partition
Customer C → Same partition

That requires data movement.

Conceptual diagram

Before shuffle:

P1 → A, B
P2 → A, C
P3 → B, C

        ↓ SHUFFLE

After shuffle:

P1 → A, A
P2 → B, B
P3 → C, C

Why wide transformations are expensive

They may involve:

  • Network transfer
  • Disk I/O
  • Serialization
  • Memory pressure
  • Spill to disk
  • Additional stages

Interview rule

Narrow transformations generally do not require shuffle; wide transformations generally require shuffle.

10. Partitions

This is extremely important.

A partition is a logical chunk of data processed by Spark.

Suppose your dataset is:

100 GB

Spark may divide it into:

Partition 1 → 10 GB
Partition 2 → 10 GB
...
Partition 10 → 10 GB

Each partition can be processed independently.

Key relationship

One partition
      ↓
One task per stage
      ↓
Processed by an executor

This is a simplified but very useful mental model.

Why partitions matter

They determine parallelism.

Too few partitions:

100 GB → 2 partitions

Only 2 tasks may run.

Cluster resources may sit idle.

Too many partitions:

100 GB → 1,000,000 tiny partitions

Too much scheduling overhead.

Goal

Find a reasonable partitioning strategy that allows efficient parallelism without excessive overhead.

Example

df.rdd.getNumPartitions()

This tells you the number of partitions in the underlying RDD representation.

For DataFrames, partitioning depends on how data was read and transformed.

11. Shuffle

Shuffle is one of the most important performance concepts in Spark.

Definition

Shuffle is the redistribution of data across partitions so that related records are brought together for operations such as joins, aggregations, and sorting.

Example

You have sales data:

Partition 1:
Customer 1 → 100
Customer 2 → 200

Partition 2:
Customer 1 → 300
Customer 3 → 400

You want:

df.groupBy("customer_id").sum("amount")

Spark must bring all records for the same customer together.

Customer 1:
100 + 300 = 400

That requires redistribution.

Why shuffle is expensive

Because data may travel:

Executor 1
    ↓ Network
Executor 2

Shuffle can involve:

  • Network communication
  • Serialization/deserialization
  • Intermediate files
  • Disk spill
  • Memory pressure

Performance principle

Avoid unnecessary shuffles and reduce the amount of data shuffled whenever possible.

This will become very important when learning:

  • Broadcast joins
  • Partition tuning
  • AQE
  • Skew handling
  • Bucketing
  • Join optimization

12. Caching and Persistence

Suppose you repeatedly use the same DataFrame.

df = spark.read.parquet("/data/sales")

filtered = df.filter("amount > 1000")

filtered.count()
filtered.groupBy("customer_id").count()
filtered.select("customer_id").show()

Without caching, Spark may recompute the upstream transformations for each action.

Without cache

Read → Filter → Count

Read → Filter → GroupBy

Read → Filter → Select

Repeated work.

With cache

filtered.cache()

Then:

filtered.count()
filtered.groupBy("customer_id").count()
filtered.select("customer_id").show()

After the first action materializes the cache, later operations may reuse the cached data.

Conceptually:

Read → Filter → Cache
                 |
       +---------+---------+
       |         |         |
      Count    GroupBy   Select

Important

cache() is lazy too.

Calling:

df.cache()

does not immediately load all data into memory.

An action is needed.

Cache vs Persist

df.cache()

Equivalent to a commonly used persistence level.

df.persist()

Allows you to specify storage levels.

Examples conceptually:

  • Memory only
  • Memory + disk
  • Disk only

When should you cache?

Cache when:

  • Same DataFrame is reused multiple times
  • Recomputing it is expensive
  • Dataset fits reasonably in available storage
  • It improves actual workload performance

When should you NOT cache?

Don't cache everything.

Caching can:

  • Consume executor memory
  • Cause eviction
  • Increase memory pressure
  • Hurt performance
  • Be unnecessary for one-time use

Important interview answer

Caching stores computed data so repeated actions can reuse it instead of recomputing the entire lineage. It should be used selectively when a DataFrame is reused and recomputation is expensive.

13. How all concepts connect together

Let's take one realistic example.

df = spark.read.parquet("/sales")

result = (
    df.filter("amount > 1000")
      .groupBy("customer_id")
      .sum("amount")
)

result.show()

Now understand what happens.

Step 1: SparkSession

spark.read.parquet(...)

SparkSession is used to access Spark.

Step 2: DataFrame

The data is represented as a DataFrame.

Step 3: Transformations

filter()
groupBy()

These build the execution plan.

Step 4: Lazy Evaluation

Spark does not immediately execute the complete operation.

Step 5: DAG

Spark builds a logical execution graph.

Read → Filter → GroupBy

Step 6: Action

show()

Triggers a job.

Step 7: Stage division

Because groupBy requires shuffle:

Stage 1:
Read → Filter

Shuffle

Stage 2:
Aggregate → Show

Step 8: Partitions

Each stage processes partitions using tasks.

Step 9: Executors

Executors execute tasks in parallel.

Step 10: Shuffle

Data is redistributed by customer_id.

Step 11: Result

The final result is returned.

That is Spark execution in one example.
